01 — Production

Flosstime scheduling system

The system that staffs nine locations, built from an empty repository and shipped to production in one summer.

Automated Systems Intern · Flosstime, Boston · Jun–Aug 2025

70%

less time spent on manual coordination

17+

More than 17 hours a week returned to managers

9 / 30+

locations, and the staff scheduled across them

The problem

Scheduling was entirely manual. Managers coordinated more than thirty staff across nine locations by hand — who was available, who was qualified, who had already been assigned somewhere else — and reworked all of it whenever anything changed.

There was no system to extend and no codebase to inherit. The first part of the job was not writing code. It was reconstructing how the manual process actually worked, including the rules nobody had written down, and turning that into something a system could enforce.

The hard part was correctness, not scheduling

Several managers edit overlapping schedules at the same time. A scheduler that quietly lets two people assign the same staff member to two places has failed at the one thing it exists to do.

I designed the data model around that constraint from the beginning: normalized PostgreSQL schemas for the relational core — staff, locations, shifts, assignments — with MongoDB for the parts of the data that did not fit a fixed shape. The schemas were built so that concurrent edits to the same schedule resolve correctly instead of overwriting one another, and so staffing rules are checked as edits happen rather than discovered afterwards, when someone is already in the wrong place.

On top of that I built the backend service layer in Python and SQL. The design priority was that requirements would keep moving — new locations would open, scheduling rules would change — so new locations and new rules can be added without rewriting the core. The parts most likely to change were deliberately kept away from the parts most expensive to break.

What I would point to

The simulation tooling. Rather than relying on manual testing, I wrote tooling that runs the scheduler against edge cases and failure scenarios: understaffed days, conflicting assignments, rule combinations that rarely occur in practice. Broken schedules surface during testing instead of in front of staff. For a system whose failures land on real people's workdays, that mattered more to me than any individual feature.

Outcome

Shipped to production before the internship ended. Managers across the nine locations rely on it daily.

What I took from the summer was mostly about ownership. Because nothing existed beforehand, every decision was mine to make and mine to defend: what to model, what the system should enforce versus leave to a human, what counted as finished. Most of the engineering went into the cases where data was incomplete, two managers disagreed, or one rule contradicted another.

02 — Multi-agent systems

Signum

Civic advisory infrastructure for autonomous fleets. A neutral layer that turns public municipal feeds into cryptographically signed, self-expiring hazard advisories any operator can consume.

Team Signifer, 3 people · AI Applications Hackathon · My scope: architecture, agent pipeline, policy compiler, evaluation harness, 3D viewer

2.9–9.1s

median, first public signal to signed advisory

1,505

passing tests across 123 modules, including property-based tests

$0.249

total model spend across 20 evaluated runs, against a $25 guard

The problem

No authoritative, machine-readable channel exists through which a city can publish a road hazard once and have every robotaxi operator receive it. The status quo is bilateral and manual — a hotline and a PDF per operator — so a city's integration cost scales linearly with the number of fleets operating in it.

The system

Signum converts public municipal feeds — National Weather Service alerts, USGS stream gauges, Austin signal-status and free-text dispatch records — into signed, self-expiring GeoJSON advisories. A multi-agent pipeline runs per-class sentinels into evidence fusion, an action proposer, an adversarial critic, and finally a deterministic policy compiler. Each advisory carries a hazard class, an action drawn from a fixed playbook vocabulary, a corroborated geometry, a validity window, and the evidence it rests on.

The engineering thesis

Models interpret; they never authorize.

No agent can publish. A Redis ACL makes the compiler the single writer to the advisory stream, enforced at the broker rather than by convention. Around it: per-class area and lifetime caps, a refusal to isolate any hospital or fire station, two-key human approval for severity-4 advisories, Ed25519 signatures any consumer can verify, and a hash-chained audit log that reconstructs every decision.

What the evaluation showed

Across all baseline runs the unadvised fleet missed the hazard; every feed-reading variant missed none. Under conflicting evidence the gate refused a 558 km² uncorroborated flood polygon against a 12 km² class cap — a refusal no human approval can override. Prompt injection embedded in feed text produced no actionable advisory, and the defence is structural rather than filtered: feed text never reaches an instruction slot.

I built the harness so each variant is a configuration flag on one codebase, which makes the ablation impossible to rig. That constraint was the point of it.

Hardening after the deadline

Two things I am glad I chased. I diagnosed a silent cross-language contract drift in which six frame validators rejected every pipeline message, then replaced the hand-written contracts on both sides with fixtures generated from the server's own builders, so the two cannot diverge undetected again. And I corrected a simulator gate that rendered corridor advisories inert, cutting hazard entries and remote-assist requests by 67% with throughput unchanged.

03 — Applied modelling

Donna

A free, client-side platform that tells a Boston homeowner whether their property is over-assessed, on what legal ground, and by when they have to file — without an appraiser or an attorney.

Originated and own the project · scope, legal-accuracy requirements, architecture

false-positive over-assessment flags, across the full dataset

266 → 119KB

266 to 119 kilobytes of initial JavaScript, gzipped

107

automated tests, including WCAG 2.1 AA invariants

Architecture

React 19, TypeScript in strict mode, Vite, Tailwind, Radix UI and pdf-lib. No backend, no accounts, no telemetry — it deploys as static assets at zero marginal cost per user, and nobody's property data leaves their browser. Two sources normalise to a single Property type: a locally extracted parcel database of 4,284 parcels and 5,338 recorded transfers, built by a node:sqlite ETL, and the Analyze Boston CKAN API read live in-browser.

The CKAN client discovers its resource ID at runtime and resolves fields through alias lists and pattern matching, because the city's schema drifts annually — TOTAL_VALUE became AV_TOTAL, and one year shipped a column named LIVING _AREA with an embedded space. Comparable cohorts are paged in full and filtered server-side by land-use class, because row order follows parcel ID geographically, which makes a truncated cohort biased rather than merely small.

The analytical engine

The core is a sales-comparison valuation. Transfers are screened for arm's-length character — nominal transfers, foreclosure deeds and master deeds are excluded, each with its reason retained for disclosure. Adjustments for time, floor area, age and condition are derived by OLS regression over local sales rather than assumed.

The model only runs when it has earned the right to: n ≥ 30, R² ≥ 0.35, elasticities inside valuer-accepted bands. Otherwise it degrades to a two-parameter time trend and says so, on screen.

Output is an interquartile range carrying a four-factor confidence score, and an assessment is flagged only above the range's upper bound. A secondary equity comparison is retained but deliberately subordinated: Massachusetts requires proof of an intentional discriminatory scheme for disproportionate-assessment claims, a threshold the Appellate Tax Board routinely rejects. Leading a homeowner toward that argument would be leading them toward losing.

Correctness that is legal, not numerical

Four jurisdictional defects found and corrected: appeal deadlines miscounted from February 1 rather than the filing date, a misstated Appellate Tax Board entry fee, unlabelled fiscal-year data, and a countdown rendered in the viewer's timezone rather than Boston's statutory cut-off. Each of those would have cost a real person a real deadline.

107 automated tests (Vitest, happy-dom) cover statutory date arithmetic, regression coefficient recovery, comparable selection, official PDF form-field population, rendered output, and accessibility invariants — single h1, heading hierarchy, label association, live-region behaviour, and state that does not depend on colour alone. CI enforces lint, test and build, and a scheduled workflow watches the municipal source for fiscal-year rollover and schema drift, opening an issue automatically.

04 — Real-time & 3D

Volta

Your reps drive a Formula 1 car around a fully rendered circuit. A webcam is the only hardware — no controller, no wearables, no markers. Clean form makes you faster.

Pose pipeline, form analyzer, 3D scene and real-time layer

33

body landmarks tracked per frame, streamed as structured events

2 reps

to self-calibrate to a new athlete's range of motion

1× → 6×

speed scaling, with boost gated on form score

How it works

Two halves talking in real time. A Python vision server tracks 33 body landmarks per frame through MediaPipe's Pose Landmarker and OpenCV; a custom curl analyzer turns those into joint angles for each arm independently and detects reps from the angle phases. The browser receives a structured JSON payload over WebSocket for every processed frame — rep count, form score, both elbow angles, rep phase, calibration status, active warnings — and a Zustand store turns that into game state. A second channel streams the annotated camera feed as MJPEG, so the athlete sees their own skeleton inside the HUD, joints turning red when the analyzer flags a problem.

The idea worth stealing

Hardcoded thresholds fit one body. The analyzer learns yours in the first two reps, then flags deviations from your baseline rather than from an average.

It records top and bottom elbow angles, lowering speed, wrist path and left–right symmetry, adds a 10% leniency margin, and from rep three onward catches incomplete curls, fast lowering, an unsteady arm, uneven sides and a drifting wrist path. Form score then drives the game: full boost above 80, medium from 50 to 80, minimal below. Doing the exercise well is the only way to win.

Things that broke, and what fixed them

  • WebGL context loss. The scene exhausted GPU memory on some machines. Reduced shadow, DPR and antialiasing cost, and added context-loss handlers.
  • Spline-to-track alignment. The car floated off the road through elevation changes. Measured the track's real bounding box and recalibrated control points against actual road mesh data, with per-frame raycasting against the asphalt keeping it planted.
  • Threading. Computer vision runs on a background thread and pushes results into the asyncio event loop, so inference never blocks the broadcast.
  • Demos that must not fail. If the pose server is not reachable within four seconds the hook falls back to simulated reps and retries every five, so the game always runs in front of an audience.

Why it generalises

Swap the curl analyzer for a squat, push-up or pitching-phase analyzer and the pipeline — detect movement, stream structured events, trigger a response — is unchanged. That event-driven design is why the project drew interest from a sports performance facility building a markerless biomechanics system.

05 — Prototype, assessed honestly

Decibels

An agentic phone relay built Deaf-first. Type a goal, a voice agent places the call, beats the phone menu, and streams every word to a live caption UI you can interrupt mid-call.

Hackathon build · shipped as a demo, not as a product

This one is included with its weaknesses attached, because the interesting engineering is in both halves.

What works, and why it was hard

The transcript revision logic is the part I am proudest of. The SDK exposes no final-versus-interim flag, so the agent infers finality from a new utterance ID, from agent speech, or from session end, then re-posts the same ID so the caption updates in place rather than duplicating. A single-worker queue keeps ordering intact.

Safety defaults were deliberate: the agent discloses it is an AI at the start of every call, the destination number always comes from the form and never from the model, and phone-menu navigation avoids language-switch and hang-up options and stays on the line when a menu is ambiguous. If the planning model fails, the goal falls back to the raw objective and the summary to a transcript-only version, so a call always completes and always returns a result.

What I would fix before it ships

It is a careful demo and an unsafe product. Those are different claims, and only one of them is on the repo.

  • Lock it down. Authentication, signed ingest events, dialing allowlist on by default, rate limiting, and real identifiers out of the repository.
  • Make it durable. Per-call IDs, Postgres for history, managed pub/sub for live events, so a page refresh never wipes a deaf user's transcript.
  • Close the accessibility loop. Let the agent ask the user mid-call instead of guessing. Verbatim relay mode, hang-up and take-over controls, hold and voicemail handling.
  • Measure outcomes. Success rate, time to reach a human, cost per call, and a simulated phone-menu test bench so every change is regression-tested.

How I work

Models interpret. They never authorize.

In Signum, no agent can publish an advisory. A broker-level ACL makes the deterministic compiler the single writer, so the guarantee holds even if every model in the pipeline is wrong at once.

Build the evaluation so you cannot cheat it.

Each variant in Signum's ablation is a configuration flag on one codebase. There is no second implementation to quietly favour, which is the only reason the numbers mean anything.

Two sources of truth will diverge. Generate one from the other.

Six frame validators were silently rejecting every pipeline message because hand-written contracts had drifted across a language boundary. I replaced both with fixtures generated from the server's own builders. The class of bug is gone, not the instance.

The happy path is rarely where the work is.

Most of the Flosstime engineering went into incomplete data, disagreeing managers and contradicting rules. Handling those quietly is what made managers trust it enough to actually use it.
